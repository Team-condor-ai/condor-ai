## 2. Cuenta de Higgsfield vinculada: diagnóstico y migración

Nota: el workflow `barbara-authcheck.yml` estaba **deshabilitado** en

### Migración a la cuenta nueva

Joaquín confirmó que ya existía una cuenta nueva y válida:
**`teamcondorcl@protonmail.com`** (plan **Plus**, **984 créditos**).

Bloqueo encontrado: el CLI de Higgsfield fijado en CI es la **0.2.3**
(pineada a propósito en julio-2026 porque la 1.0.0 introdujo cambios
rompientes: workspace obligatorio + auth flow nuevo incompatible — ver
`services/barbara/barbara_higgsfield_cli_fix.md` en memoria). Esta
máquina solo tenía la **1.1.23** instalable vía `npm i -g`, y
`npm i -g @higgsfield/cli@0.2.3` falla igual que en julio: descarga
truncada del binario (`hf_0.2.3_windows_amd64.tar.gz`) desde el
`install.js` del paquete npm.

**Solución (nueva, para dejar registrada):** el binario SÍ se puede bajar
completo con `curl` directo desde GitHub Releases, sin pasar por el
`install.js` de npm que falla:

```bash
curl -fL -o hf.tar.gz \
  https://github.com/higgsfield-ai/cli/releases/download/v0.2.3/hf_0.2.3_windows_amd64.tar.gz
tar -xzf hf.tar.gz   # produce hf.exe
```

Con ese `hf.exe` (0.2.3 real, idéntico al de CI) se corrió
`auth login` → abrió el navegador, Joaquín inició sesión con la cuenta
nueva → `account status --json` confirmó
`teamcondorcl@protonmail.com / plus / 984 créditos`.

Luego (a mano, no con `services/barbara/reauth.sh` porque ese script
tiene hardcodeado el repo viejo `joaquinmunozs/condor-ai`):

1. `openssl enc -aes-256-cbc -pbkdf2 -salt` con una llave nueva
   (`openssl rand -hex 32`) sobre `~/.config/higgsfield/credentials.json`
   → `services/barbara/hf-creds.enc`.
2. `gh secret set HF_CREDS_KEY -R Team-condor-ai/condor-ai` con esa
   llave nueva.
3. Commit + push de `hf-creds.enc`.
4. Run real de `barbara-authcheck.yml` en CI → log confirmó
   `"Higgsfield: autenticación OK ✅"` (no solo "success" de fachada:
   se verificó el texto real del log, no solo el conclusion del run).

**Commit:** `5f3aef8` — *Barbara: rotar credenciales de Higgsfield a la
cuenta nueva (teamcondorcl@protonmail.com)*.

⚠️ **Pendiente de que Joaquín corrija `reauth.sh`** si se vuelve a

## 3. Sesión de Higgsfield: por qué no es indefinida

Se le explicó a Joaquín (y queda registrado acá porque es relevante para
clientes, no solo para Cóndor): la sesión de Higgsfield es OAuth
(`access_token` + `refresh_token`), no una API key fija.

- Se auto-renueva sola mientras algo la usa seguido (cada corrida de
  `barbara.yml`, `reels.yml` o `barbara-authcheck.yml` refresca el
  token, y si rotó, se re-cifra y se sube solo).
- **Ya murió una vez** en producción (jun-jul 2026): quedó inactiva y el
  refresh_token dejó de servir, "Session expired" / "Not authenticated".
  Hubo que re-loguear a mano.
- Existe una alternativa que NUNCA vence (Higgsfield Cloud API, key
  `Authorization: Key {id}:{secret}`), pero se descartó en julio-2026
  porque le faltan modelos clave (Nano Banana, Veo — 404), no genera voz
  nativa para los reels, y cobra aparte del plan (pay-as-you-go, no usa
  los créditos ya pagados).
- Es **una sola cuenta compartida**: si la sesión muere, se corta la
  generación para Cóndor y para TODOS los clientes de Bárbara a la vez,
  no por separado.

## 4. Chequeo diario endurecido

`barbara-authcheck.yml` corría solo Lun-Vie (`cron: '0 11 * * 1-5'`).
Se cambió a **todos los días** (`cron: '0 11 * * *'`) — cada corrida usa
y renueva el `refresh_token`, así que correr también el fin de semana
reduce la ventana de inactividad que fue la causa raíz de que la sesión
venciera la vez pasada. Sigue siendo puramente cron, sin depender de
ningún webhook, tal como pidió Joaquín.

**Commit:** `f238f35` — *Barbara: authcheck de Higgsfield todos los días,
no solo Lun-Vie*.
